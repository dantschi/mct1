Rückblick: Was wir bisher blind genutzt haben

  • Maschinenbefehl immer exakt 32 Bit breit
  • Instruction Formats: R, I, S, B
  • Register lesen und überschreiben (t0, s0, …)
  • ALU kann addieren und vergleichen
  • PC als logischer Zeiger im Code
# Wir wissen, WAS dieser Befehl tut:
add t0, t1, t2

# Aber WIE wird aus 0x007302B3 die ALU aktiviert?

Bisher Magie: Wer öffnet das Register File? Wer konfiguriert die ALU? Die CPU war Blackbox — heute öffnen wir sie.

Die Blackbox öffnen

  • Ein realer Prozessor: Milliarden Transistoren
  • Mikroskopische „Autobahnen“ — für Menschen nicht greifbar
  • Abstraktion: Blockdiagramme statt einzelner Elektronen
  • Fokus: Datenflüsse und Vernetzung der Komponenten

Ingenieure abstrahieren zu Blöcken: Register File, ALU, Multiplexer — verbunden durch 32-Bit-Leitungsbündel.

Was ist ein Datenpfad (Datapath)?

  • Physikalische „Rohrleitung“ des Prozessors
  • Alles, was Daten verarbeitet oder transportiert: ALU, Register File, Speicher, Multiplexer
  • Nicht dazu: die Control Unit (Steuerwerk) — sie dirigiert nur
  • Der Datenpfad begrenzt die Maximalleistung des Chips

Datenpfad = Nutzdaten-Fluss. Steuerwerk = Hebel an den Ventilen. Heute exklusiv das Rohrleitungssystem.

Der Single-Cycle-Prozessor

  • Viele Steuerungsarten: Pipelining, Multi-Cycle, …
  • Heute: didaktisch zentrales Modell — Single-Cycle
  • Ein Maschinenbefehl in exakt einem Taktzyklus
  • Bei jeder steigenden Taktflanke ist ein Befehl fertig
  • Leicht verständlich, modern oft ineffizient (Vertiefung später)

Ein Takt: Fetch bis Write-Back. Moderne Chips arbeiten anders — das Modell bleibt der Schlüssel zum Verständnis.

Die 5 Phasen

  • Logisch fünf Stationen, auch wenn alles in einem Takt geschieht
  • Universelles Schema vieler Architekturen
  • Datenfluss strikt von links nach rechts (Write-Back als Rückführung)
  • Abkürzungen: IF, ID, EX, MEM, WB

Heiliger Gral der Rechnerarchitektur: Instruction Fetch, Decode, Execute, Memory, Write-Back — von Mikrocontroller bis Server.

Phase 1: Instruction Fetch (IF)

  • 32-Bit-Maschinencode aus dem Speicher holen
  • PC liefert die physikalische Adresse
  • Instruction Memory liefert die Instruktion
  • Parallel: Vorbereitung \(PC + 4\) für den nächsten Befehl

Noch „dumm“: Adresse lesen, Wort liefern. Ein kleiner Addierer hält bereits \(PC+4\) bereit.

Phase 2: Instruction Decode (ID)

  • 32-Bit-Wort entschlüsseln, Operanden bereitstellen
  • Felder: opcode, rs1, rs2, …
  • rs1/rs2 an das Register File — Werte auf die Datenleitungen
  • Control Unit erzeugt Steuersignale aus dem Opcode

Opcode analysieren, Registeradressen herausgreifen, Werte auf RD1/RD2 legen — kombinatorisch (reine Gatterlaufzeiten, ohne Taktzustand).

Phase 3: Execute (EX)

  • Mathematische oder logische Arbeit: die ALU
  • R-Type: zwei Registerwerte verknüpfen
  • Load/Store: Zieladresse = Base + Offset
  • Branch: Vergleich (z. B. Differenz auf Null)

Die ALU rechnet nicht nur bei add: bei lw/sw berechnet sie die RAM-Adresse (Base + Offset).

Phase 4: Memory (MEM)

  • Kommunikation mit dem Datenspeicher
  • Relevant für lw, sw und Verwandte
  • Andere Befehle: Bypass am RAM vorbei
  • lw: lesen; sw: schreiben an ALU-Adresse

Bei add bleibt der Datenspeicher abgeriegelt; das ALU-Ergebnis fließt parallel weiter zum Write-Back.

Phase 5: Write-Back (WB)

  • Fertigen Wert in Zielregister rd ablegen
  • Rückführung zum Register File (visuell „nach links“)
  • add: ALU-Ergebnis; lw: RAM-Daten
  • beq/sw: kein Register-Schreiben — Phase inaktiv

Mit dem Write-Back ist der Befehl vollständig abgearbeitet — bereit für den nächsten Takt.

Fetch und R-Type-Datenpfad

  • Aufbau des Hardware-Schaltplans beginnen
  • Fetch: Instruktion holen
  • PC und PC+4-Addierer
  • Verschaltung für add/sub
  • Timing innerhalb eines Taktes

Vom PC links nach rechts zum reinen Rechenpfad — R-Type ohne Datenspeicher.

Der Startpunkt: Der PC

  • Program Counter: spezielles 32-Bit-Register
  • Speichert den Ausführungszustand (State)
  • D-Flip-Flops: Update nur bei positiver Taktflanke
  • Während des Taktes: stabile Adresse am Ausgang

Anker des Datenpfads. Flankengetriggert: neue Adresse einfrieren, bis zum nächsten Tick halten.

Instruction Memory (Befehlsspeicher)

  • Erstes Bauteil hinter dem PC
  • PC-Wert am Adress-Eingang
  • Single-Cycle-Modell: kombinatorische Ausgabe der Instruktion
  • Während der Ausführung: nur Lesen

Adresse anlegen — nach kurzer Verzögerung liegt das 32-Bit-Wort am Ausgang. Fetch erledigt.

PC-Inkrementer (\(PC + 4\))

  • Separater Hardware-Addierer (nicht die Haupt-ALU)
  • Fest verdrahtet: immer \(+4\) zur PC-Adresse
  • Ergebnis zurück an den PC-Eingang — wartet auf die nächste Flanke

Kabel splitten: ein Strang zum Instruction Memory, einer zum \(+4\)-Addierer. Flip-Flops übernehmen erst beim Tick.

R-Type-Refresher

  • Instruktion liegt auf den Leitungen
  • Ziel: add rd, rs1, rs2 physikalisch
  • Bits 19:15 = rs1, 24:20 = rs2, 11:7 = rd
Bits Feld
31:25 funct7
24:20 rs2 (lesen)
19:15 rs1 (lesen)
14:12 funct3
11:7 rd (schreiben)
6:0 opcode

32-Bit-Kabel aufspleißen: drei 5-Bit-Bündel für rs1, rs2, rd zum Register File.

Register lesen (ID)

  • Zwei Lese-Ports A1 und A2
  • rs1/rs2 direkt angeschlossen
  • Kombinatorisch: Inhalte auf RD1 und RD2
  • Operanden physikalisch isoliert

Asynchron in der ID-Phase: Spannung an den Ports — Werte auf den Datenausgängen.

Die ALU (EX)

  • RD1 und RD2 in die ALU-Eingänge
  • Sofortige Verknüpfung (kombinatorisch)
  • Operation via ALU-Control (aus opcode/funct3)
  • Ergebnis am ALU-Ausgang

Kein Zwischenspeicher in der ALU: Gatterlaufzeiten, dann steht das Resultat. Execute-Phase erreicht.

Write-Back (WB)

  • Ergebnis zurück zur Werkbank
  • Leitung vom ALU-Ausgang zum WD-Port (Write Data)
  • Visuell der „rückwärts“-Pfad auf dem Plan
  • Bits warten am Register File

Bei R-Type wird MEM umgangen. Daten stehen an der Tür — noch nicht geschrieben.

Zieladresse (rd)

  • Schreibfach: Bits 11:7 (rd) an Port A3
  • Hardware für R-Type damit vollständig verdrahtet

A3 sagt: „Schreibe die anliegenden Daten in Fach Nummer \(rd\).“

Das RegWrite-Signal

  • Schutzventil: Steuerpin RegWrite (1 Bit)
  • RegWrite \(= 1\): bei nächster Flanke in rd speichern
  • RegWrite \(= 0\): Signale prallen ab (wichtig für sw/beq)

Ohne RegWrite würde jedes Tick Register überschreiben. Nur bei erlaubtem Write-Back auf 1.

Der fertige R-Type-Pfad

  • Strom: PC → Instruction Memory → Register lesen → ALU → Write-Back
  • Kein Zugriff auf den Data Memory

Synchronisierter Datenfluss ohne RAM. Als Nächstes: Timing — wann wird wirklich gespeichert?

Timing im Single-Cycle

  • Gatter arbeiten ununterbrochen; Signale breiten sich aus
  • Erst wenn EX/WB stabil: Ergebnis am Register-Eingang
  • Steigende Flanke am Taktende:
    • Register File speichert (wenn RegWrite \(= 1\))
    • PC übernimmt \(PC+4\)
  • Sofort Start des nächsten Befehls

Während der Periode: Kombinatorik. Flanke: Zustände einfrieren. (Gantt-Darstellung bewusst als Phasen-Kette — handout-tauglich.)

Warum überschreiben wir nichts vorzeitig?

  • Fall: rd = rs1, z. B. addi t0, t0, 1
  • Alter Wert wird gelesen, durch ALU, steht am Schreib-Port
  • Flip-Flops ändern den Ausgang erst mit der Flanke
  • Deshalb ist \(a = a + b\) gefahrlos
t0 = t0 + t1;
// Lesen und Schreiben im selben Takt — Flankensteuerung rettet uns

Klassische Klausurfrage: Lesen und Schreiben desselben Registers im Takt. Flankensteuerung hält den alten Wert stabil bis zum Tick.

Was passiert mit Phase 4 (MEM)?

  • Im reinen R-Type-Pfad fehlt der Data Memory
  • MEM existiert logisch, physikalisch Bypass
  • ALU-Ergebnis direkt zum Write-Back
  • Nächster Schritt: RAM für Load/Store einhängen, ohne R-Type zu zerstören

Ungenutzte Blöcke bleiben abgemeldet. Load/Store brauchen denselben Pfad — elegant erweitert, nicht neu erfunden.

Der Load/Store-Datenpfad

  • Konstanten (Immediates) in die ALU
  • Data Memory einbinden
  • Erster Ressourcenkonflikt — Multiplexer
  • Datenwege für lw und sw
  • Steuersignale MemRead / MemWrite

Neue Leitungen erzeugen Kollisionen an ALU-Eingängen und Write-Back. Multiplexer als elektrische Weichen — nächster Bauabschnitt.

Das Problem mit I-Types

  • R-Type: beide Operanden aus dem Register File (rs1, rs2)
  • I-Type (lw, addi): kein rs2 — stattdessen 12-Bit-Immediate
  • Die ALU hat 32-Bit-Eingänge
  • Die Konstante muss aus dem Befehlswort in die ALU gelangen
Bits Feld
31:20 imm[11:0] → diese 12 Bits müssen in die ALU
19:15 rs1
14:12 funct3
11:7 rd
6:0 opcode

Für lw braucht die ALU Base + Offset. 12 Drähte an einen 32-Bit-Eingang zu löten reicht nicht — 20 Leitungen fehlen. Sign-Extension in Hardware ist nötig.

Immediate Generator (ImmGen)

  • Vereinfacht für I-Type: Bits 31:20 als 12-Bit-Immediate
  • S-/B-Formate nutzen andere Bitfelder — ImmGen kennt mehrere Layouts
  • 12-Bit-Eingang, 32-Bit-Ausgang
  • Aufgabe: Vorzeichenerweiterung (Sign-Extension) in Hardware
  • Beim I-Type: Bit 31 wird auf die oberen 20 Bits kopiert

Einstieg am I-Type (addi, lw): ImmGen fächert das Vorzeichenbit auf. Bei Branches/Stores greifen andere Immediate-Layouts — dasselbe Bauteil, andere Verdrahtung der Instruktionsbits.

Der erste Konflikt (Kollision)

  • Zwei 32-Bit-Signale wollen denselben ALU-B-Eingang
  • add: Signal aus RD2 (Register File)
  • lw/addi: Signal aus ImmGen
  • Beide Kabel auf einen Kontakt = Kurzschluss

Klassischer Ressourcenkonflikt. Lösung: elektronische Weiche — Multiplexer.

MUX 1: ALU-Source (ALUSrc)

  • Multiplexer: mehrere Eingänge, ein Ausgang
  • Steuerpin ALUSrc
  • ALUSrc = 0: RD2 zur ALU
  • ALUSrc = 1: Immediate zur ALU

MUX wie eine Bahnweiche: Control Unit stellt ALUSrc, Kurzschluss vermieden.

Load Word (lw) — die Adressierung

  • Mit MUX kann die ALU Konstanten verarbeiten
  • Bei lw: ALU berechnet nur die RAM-Adresse (Base + Offset)
  • Ergebnis = Hausnummer, kein „normales“ Rechenergebnis
  • Diese Adresse geht an den Datenspeicher
lw t0, 12(s1)
# 1. ALUSrc = Immediate (12)
# 2. ALU: s1 + 12
# 3. Adresse am ALU-Ausgang

Base am A-Eingang, Offset über ImmGen/MUX am B-Eingang — Adresse für den Data Memory.

Data Memory (Datenspeicher)

  • Block in der MEM-Phase: Data Memory (RAM)
  • Address: Ausgang der ALU
  • Write Data: für Store
  • Read Data: gelesene Daten
  • Im Modell: kombinatorisches Lesen (wie Instruction Memory)

Didaktisches Modell: getrennte Instruction- und Data-Memory-Blöcke. Adresse anlegen — Daten auf Read Data.

Daten aus dem RAM lesen

  • Read Data = Wert des lw
  • Write-Back: Leitung zurück zum WD-Port des Register Files
  • Ziel: bei der Flanke in rd speichern
  • Kollision: dort liegt bereits das ALU-Rückführkabel

Zwei Kandidaten am WD-Port: ALU-Ergebnis (R-Type) vs. RAM-Daten (lw).

Der zweite Konflikt (MemtoReg)

  • WD empfängt nur ein 32-Bit-Signal
  • R-Type will ALU-Ergebnis; lw will RAM-Daten
  • Lösung: zweiter MUX vor dem Register File
  • Steuersignal: MemtoReg

MemtoReg = 1: RAM durchlassen; = 0: ALU durchlassen.

Store Word (sw) — der Pfad

  • sw: rs2 liefert die zu speichernden Daten
  • Wert liegt schon auf RD2 (ID-Phase)
  • Abzweig von RD2 zum Write-Data-Port des RAM (Bypass um die ALU)
  • ALU berechnet parallel Base + Offset als Adresse

Adresse wie bei lw; Datenpfad von RD2 direkt in den RAM-Schreibeingang.

Die Signale MemWrite und MemRead

  • Speicher braucht Schutzpins wie das Register File
  • MemWrite = 1: bei Flanke schreiben
  • MemRead = 1: Daten auf Read Data ausgeben
  • Bei add: beide 0 — RAM inaktiv

RD2 wackelt oft am Speicher. Nur bei echtem Store öffnet MemWrite den Schreibpfad.

Store und das Register File

  • sw schreibt in den RAM, nicht in Register
  • S-Type: kein rd — auf dem rd-Kabel liegt Müll
  • RegWrite muss bei Store zwingend 0 sein
  • Sonst würde die Flanke ein Zufallsregister überschreiben
Ohne RegWrite=0:
MUX MemtoReg leitet immer etwas weiter —
Store wuerde Register mit Muell beschreiben.

Zusammenspiel der Steuersignale: Store = RAM schreiben, Register File abgeriegelt.

Der Load/Store-Pfad erweitert

  • Rechnen (R-Type) und Speicherzugriff (I-/S-Type)
  • Multiplexer regeln den Verkehr
  • Es fehlt: dem PC das Springen beibringen

Lineare Programme sind machbar. Nächste Stufe: Kontrollfluss — Branch-Datenpfad.

Der Branch-Datenpfad

  • Hardware für bedingte Entscheidungen
  • Problemstellung beq
  • ALU als Komparator (Zero-Ausgang)
  • Zweiter Addierer für das Branch-Target
  • Logische Verknüpfung der Sprungbedingung

Register vergleichen und PC dynamisch setzen — wenn die Bedingung wahr ist.

Das Branch-Problem (beq)

  • beq rs1, rs2, Label: zwei Aufgaben in einem Takt
  • Bedingung: sind rs1 und rs2 gleich?
  • Navigation: neues PC-Ziel = aktueller PC + Offset
  • Beides braucht Addition/Subtraktion — nur eine Haupt-ALU
# Hardware-Sicht:
# 1. rs1 == rs2 ?
# 2. PC_neu = PC + Offset
# wenn (1): PC = PC_neu

Ressourcenkonflikt: Vergleich und Target-Berechnung gleichzeitig — zweiter Addierer nötig.

Vergleich in Hardware (Subtraktion)

  • Trick: Subtraktion statt direktem Gleichheitstest
  • ALU: Ergebnis \(= rs1 - rs2\)
  • Identisch \(\Rightarrow\) Ergebnis \(= 0\)
  • Dann war beq erfolgreich
Wenn A == B, dann A - B == 0

Ungleich null \(\Rightarrow\) ungleich. Hardware prüft, ob das ALU-Ergebnis nur Nullen enthält.

Die ALU und der Zero-Ausgang

  • Dedizierter 1-Bit-Ausgang: Zero (oft „Zero-Flag“ genannt)
  • NOR über alle 32 Ergebnisbits
  • Alle Bits 0 \(\Rightarrow\) Zero \(= 1\)
  • Sonst Zero \(= 0\)
  • Das Datenwort der ALU wird bei Branches typisch verworfen

Hinweis Terminologie: In RISC-V-Datenpfaden ist Zero ein ALU-Ausgangspin, kein separates Statusregister wie bei x86. Ein Draht = Wahrheitsbit für den Branch.

Zieladresse berechnen (Navigation)

  • Haupt-ALU ist mit der Subtraktion belegt
  • Offset steckt im B-Type als zerrissenes Immediate
  • ImmGen setzt zusammen und sign-extended auf 32 Bit
  • Negative Offsets: Sprünge „nach oben“ (Schleifen)
Bits Feld
31:25 imm[12\|10:5]
24:20 rs2
19:15 rs1
14:12 funct3
11:7 imm[4:1\|11]
6:0 opcode

ImmGen kennt auch das B-Format. Zweierkomplement erlaubt rückwärts gerichtete Sprünge.

Offset-Aufbereitung (Shift Left 1)

  • Immediate vor der PC-Addition um 1 Bit nach links (\(\cdot 2\))
  • Instruktionen enden nie auf ungerader Byte-Adresse
  • Unterstes Bit der Distanz ist implizit 0 — Compiler speichert es nicht
  • Hardware hängt die 0 per Shift an — größere Sprungreichweite

Vereinfachte Darstellung für RV32I: Wortausrichtung und B-Immediate-Skalierung. Details im Lehrbuchdiagramm (Patterson & Hennessy) und in Ripes nachvollziehbar.

Der Branch-Addierer

  • Zweiter, dedizierter Addierer (Haupt-ALU blockiert)
  • Eingang 1: aktueller PC
  • Eingang 2: aufbereitetes Offset
  • Ausgang: Branch Target

Silizium für Parallelität: Vergleich und Target-Berechnung im selben Takt.

Der dritte Konflikt (PC-Update)

  • Am Taktende braucht der PC eine neue Adresse
  • Kandidat 1: \(PC + 4\)
  • Kandidat 2: Branch Target
  • Zwei Kabel am PC-Eingang — wieder MUX nötig

Dritter Weichensteller: direkt vor dem PC-Register.

MUX 3: PC-Source (PCSrc)

  • MUX vor dem PC-Eingang
  • Port 0: linear (\(PC + 4\))
  • Port 1: Branch Target
  • Steuersignal: PCSrc

Wer stellt PCSrc? Nur bei echtem, erfolgreichem Branch umschalten.

Wer steuert PCSrc? (Die Logik)

  • Zwei Bedingungen gleichzeitig:
    • Befehl ist Branch (Control: Branch \(= 1\))
    • Vergleich erfolgreich (ALU: Zero \(= 1\))
  • Verknüpfung mit AND-Gatter
  • \(\mathrm{PCSrc} = \mathrm{Branch} \land \mathrm{Zero}\)

Zufällige ALU-Null bei sub darf nicht springen — nur Branch-Opcode plus Zero.

Trace: Branch Taken

  • Bedingung wahr: beq, Register gleich
  • AND \(= 1\), MUX auf Port 1
  • Nächste Flanke: Target in den PC — Sprung erfolgt

Zero leuchtet, Branch leuchtet, AND feuert, Weiche klappt — PC übernimmt das Label.

Trace: Branch Not Taken (Fall-Through)

  • Bedingung falsch: Register ungleich
  • Zero \(= 0\) → AND \(= 0\)
  • MUX bleibt auf Port 0: \(PC + 4\)
  • Target-Adresse verpufft ungenutzt

Fall-Through: lineare Fortsetzung. Eleganz reiner Kombinatorik plus einer Flanke.

Unbedingte Sprünge (jal) — Ausblick

  • jal braucht etwas mehr Verdrahtung als beq
  • Bedingungslos: PCSrc gezielt auf Target
  • Rückflugticket: \(PC+4\) muss nach rd (meist ra)
  • Extra-MUX/Kabel zum Write-Back — im Blockdiagramm vereinfacht
  • In Ripes im Labor sichtbar
jal ra, Label:
  PC = Target
  ra = PC+4

Vereinfachung: Wir blenden die jal-Write-Back-Kabel hier aus; Einheit 4 und Ripes zeigen den Link-Pfad.

Die Anatomie ist fast komplett

  • Speicher/Register: PC, Instruction Memory, Data Memory, Register File
  • Rechenwerke: Haupt-ALU, Branch-Addierer, \(+4\)-Addierer
  • Weichen: drei Multiplexer (ALUSrc, MemtoReg, PCSrc)
  • Branch-Logik: Zero und AND

Als Nächstes: Teilpfade zum Master-Diagramm und die Rolle der Control Unit.

Der komplette Datenpfad

  • Alle Teilpfade zu einem System
  • Klassisches Architektur-Diagramm (Patterson & Hennessy)
  • Control Unit als Dirigent der Steuersignale
  • Schwäche des Single-Cycle: Timing / Taktperiode
  • Ausblick: warum Pipelining nötig wird

Finale Theorie: Steuerwerk und Datenpfad zusammen. Das vereinfachte Gesamtbild folgt nach der Ressourcen-/MUX-Zusammenfassung; danach Timing und Pipelining-Ausblick.

Der Ressourcenkonflikt (Zusammenfassung)

  • Drei Teilpfade: R-Type, Load/Store, Branch
  • Problem: keine eigene ALU/Register File pro Befehlstyp
  • Transistoren kosten Fläche, Energie und Geld
  • Lösung: Pfade überlagern — gemeinsame Nutzung (Reuse)
  • Dieselbe ALU: mal Addition, mal Adresse, mal Vergleich

Drei ALUs wären absurd teuer. Eine ALU dient nacheinander ganz unterschiedlichen Befehlen — das ist die Genialität der Architektur.

Multiplexer: Die Weichensteller

  • Wie vermeiden wir Chaos beim Zusammenlegen der Kabel?
  • Antwort: unsere drei Multiplexer
  • Verkehrspolizisten des Datenpfads
  • Ohne sie: Kurzschlüsse an teuren Eingängen (ALU, PC, Register)

Zwei Quellen, ein Ziel: Kabel aufschneiden, MUX dazwischen, ein sauberes Ausgangskabel.

Der komplette Datenpfad (Patterson & Hennessy)

  • Single-Cycle Datapath nach Patterson und Hennessy (RISC-V Edition; Signalnamen dieses Kurses)
  • Harris & Harris (Kursliteratur) nutzen teils andere Namen (ResultSrc statt MemtoReg, ImmSrc, …) — Konzept identisch
  • Vereint IF, ID, EX, MEM, WB; drei MUX-Weichen hervorgehoben
  • Rote gestrichelte Linien: Steuersignale der Control Unit

Meisterdiagramm der Rechnerarchitektur — hier didaktisch verdichtet. Signalnamen folgen Patterson/Hennessy; in Ripes heißen einige Signale anders (Mapping-Folie).

P&H-Diagramm und Ripes: Mapping

Das Lehrbuch-Diagramm und der Ripes-Single-Cycle-Prozessor sind nicht baugleich. Merken Sie sich die Entsprechungen:

Patterson/Hennessy (Folien) Ripes (Single-Cycle)
ALU-Zero + AND mit Branch → PCSrc Dedizierte Branch-Vergleichseinheit (alle Branch-Typen)
Separater Branch-Addierer Branch-Ziel oft über Haupt-ALU (PC als Op1)
2-Wege-MUX MemtoReg Oft 3-Wege-Write-Back-MUX (Reg wr src: ALU / Mem / PC+4)
Signalnamen MemtoReg, MemRead, … teils andere Bezeichner (Tooltips lesen!)
Farben: beliebig 1-Bit-Signale: grün = 1, grau = 0 (kein „rot = 0“, kein „ausgegraut = \(X\)“)

Don’t Care (\(X\)) ist ein Entwurfskonzept der Wahrheitstabelle — der Simulator zeigt immer einen konkreten Bitwert.

Labor: Paper-&-Pencil nach P&H, Verifikation in Ripes mit Mapping. Nicht erwarten, dass Zero+AND und Branch-Addierer 1:1 sichtbar sind.

Weiche 1: ALUSrc

  • Vor der Haupt-ALU
  • Entscheidung: womit rechnen?
  • 0: zweites Register (RD2)
  • 1: Immediate aus ImmGen
add  t0, t1, t2  -> ALUSrc = 0
addi t0, t1, 5   -> ALUSrc = 1

R-Type: Registerkabel. I-Type/lw: ImmGen-Pfad.

Weiche 2: MemtoReg

  • Rechts vor dem Write-Back
  • Entscheidung: was nach rd?
  • 0: ALU-Ergebnis
  • 1: RAM-Daten
  • Bei sw/beq: Stellung oft Don’t Care (weil RegWrite = 0)
add t0, t1, t2  -> MemtoReg = 0
lw  t0, 0(s1)   -> MemtoReg = 1

Ohne RegWrite prallt Müll am Register File ab — Don’t Care ist ungefährlich.

Weiche 3: PCSrc

  • Oben links vor dem PC
  • 0: \(PC + 4\) (Fall-Through)
  • 1: Branch Target
  • Einzige Weiche, die auch vom ALU-Zero abhängt (AND mit Branch)
add ...              -> PCSrc = 0
beq ... (genommen)   -> PCSrc = 1

Navigator des Prozessors: linear weiter oder Sprung — Control plus Live-Ergebnis der ALU.

Die Steuersignale (Control)

  • Typisch: RegWrite, MemRead, MemWrite, ALUSrc, ALUOp, …
  • Quelle: Control Unit (Steuerwerk)
  • Liest den Opcode und erzeugt die Weichen-/Speicher-Signale
  • Detailbau der Control Unit: Einheit 6

Dirigent von oben: Opcode analysieren, Multiplexer und Schreibfreigaben in Nanosekunden setzen.

Das Timing-Problem (Critical Path)

  • Single-Cycle: alles in einem Takt
  • Nächste Flanke erst, wenn das letzte Signal stabil ist
  • Taktperiode \(\ge\) kritischer Pfad (längste Verzögerungskette)
  • Zu schneller Takt: nächster Fetch vor Write-Back — Absturz

Die Taktfrequenz muss zum langsamsten Befehl passen — Critical Path diktiert die MHz.

Welcher Befehl ist der langsamste?

  • add: Fetch → Decode → ALU → Write-Back (RAM idle)
  • beq: Fetch → Decode → ALU/Branch-Addierer → PC
  • Verlierer: lw — alle Stationen inkl. Data-Memory
  • Gesamte CPU muss so langsam takten, dass lw in einen Zyklus passt

Zwei Speicherzugriffe plus langes Write-Back-Kabel: lw bestimmt den kritischen Pfad.

Das Ende des Single-Cycle

  • Langer Takt für lw verschwendet Zeit bei schnellen Befehlen
  • add ist früh fertig — ALU wartet bis zum Tick
  • Ineffiziente Hardware-Nutzung
  • Für hohe GHz: Architektur umbauen

Todesstoß des Single-Cycle in der Praxis: teures Silizium steht oft still.

Ausblick: Pipelining (Fließband)

  • Langen Zyklus in fünf kurze Takte zerlegen
  • Fließband: während Befehl 1 in ID ist, startet Befehl 2 in IF
  • Alle Blöcke arbeiten gleichzeitig an verschiedenen Befehlen
  • Vertiefung: Einheit 7

Heute bleibt das übersichtliche Single-Cycle-Modell. Pipelining kommt in Einheit 7.
